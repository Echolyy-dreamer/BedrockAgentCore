01

当一个 Agent 系统行为异常

Agent 系统的最终表现往往只有三类：输掉比赛、回答错误、执行失败。但这类症状从不告诉你病因在哪——它可能出在完全不同的四层中的任何一层：

L1 · 世界状态
World State
引擎/上游送来的数据本身：字段、坐标、编号、语义是否可被无歧义理解
→
L2 · 上下文
Context
把世界压缩成模型输入的过程：摘要、提示词、上下文工程
→
L3 · 推理
Reasoning
模型基于所见输入做出的决策：指令选择、参数、对状态的响应性
→
L4 · 执行
Execution
把模型输出转换成最终动作的最后一环：解析、校验、落地
没有分层埋点时：你只能看到错误结果（0:2 的比分），然后对着结果猜测——是模型不行？是 Prompt 不对？还是引擎有 bug？有了分层埋点后：每一层的输入与输出都被记录，错误在哪一层产生、从哪一层开始失真，第一次可以被日志回答，而不是靠猜。

下面这场足球赛是这套方法最完整的样本：5 个位置智能体（GK / DEF / MID / FWD1 / FWD2）各自独立决策，共享同一个游戏世界，最终以 0:2 落败。整场比赛留下了 362 个完整决策周期，四个埋点横跨全部周期——没有比这更适合讲分层可观测性的场景了。

02

四个埋点：把链路切成四段

每个位置智能体都是一条独立决策流水线：读世界 → 压缩世界 → 让模型决策 → 把决策落成指令。四个埋点恰好沿这条链放置，每个埋点对应 L1~L4 中的一层：

埋点 1 · 入参（L1）
原始 game_state
引擎发来的完整世界状态（球、10 名球员、比分、模式）——记录"真实世界长什么样"
→
埋点 2 · 中间态（L2）
summarize_state 摘要
喂给 LLM 的精简文本——记录"模型看到的世界长什么样"
→
埋点 3 · 模型输出（L3）
LLM 原始指令
Nova 模型返回的 JSON——记录"模型想做什么"
→
埋点 4 · 落地（L4）
解析后下发指令
parse_commands 处理后的最终命令——记录"系统真正做了什么"
埋点 1 = 世界层真实输入埋点 2 = 上下文层输出埋点 3 = 推理层输出埋点 4 = 执行层输出

四个切面两两对比，就能回答最尖锐的问题：当一场比赛打得不对，是世界错了、摘要错了、模型错了，还是指令落地错了？下文 7 个缺陷案例，全部来自这些切面之间的错位。

04

七处失真，四层归属

7 个缺陷分布在四层里，L3 推理层还伴随一组独立的决策行为问题（复读、无球动作、错位指令）。逐层拆解，每一层都用真实日志作证。

LAYER 1
世界状态层 · World Model / Contract Failures
7 个缺陷中有 2 个的根在这里：字段语义、坐标尺度、编号唯一性。错在这一层，Agent 代码读得再对也救不回来。

BUG 1 agentId 两队复用：编号不是全局唯一 契约缺陷 · 引擎/API Layer 1 · 发现于 埋点 1 · 原始 game_state
agentId 无队伍维度 possessionAgentId 无法判队 target_player_id 无上下文

发现：第一条原始 game_state 就暴露了结构性问题——主队和客队的球员编号完全一样。home 有 agentId_0~4，away 也有 agentId_0~4。整个比赛中 10 名球员的编号只有 5 个取值，且每个编号对应两名球员。

影响：凡是依赖编号定位球员的字段全部带上歧义——球权归属（possessionAgentId）、传球/盯防目标（target_player_id）都只给一个编号，无法判断指的主队还是客队。这是后文 BUG 4、BUG 7 的上游结构性前提：同一套代码在正确读取编号时，也永远无法区分两个同号球员。

BUG 3 摘要硬编码球门坐标：362/362 周期输出 "Your goal at x=-55" 胶水层 Bug · 摘要实现 Layer 2 · 发现于 埋点 2 · 摘要文本

BUG 4 持球归属 100% 误标：对手持球被摘要写成 "MY player N" 胶水层 Bug · 摘要实现 Layer 2 · 发现于 埋点 2 × 埋点 1 交叉验证
next() 取同编号第一个球员 players 数组 home 永远在前 摘要恒判本队持球

发现：把摘要的持球声明（"held by MY player N"）与原始 game_state 交叉验证：用"同编号两名球员中谁离球最近"判定真实持球方。237 个标 MY 的周期里，90 个周期真实持球方是客队——摘要 100% 把对手持球写成了本队持球。

根因（代码级）：线上版 get_possession_info() 用 next(p for p in players if idx(p)==possession_id) 取持球人。而 game_state 的 players 数组永远是 home 在前、away 在后（见 BUG 1 日志），next() 必然命中主队同编号球员 → _is_my_team() 恒为 True → 摘要恒写 MY。

影响：防守端最致命。67 个发出防守指令（PRESS_BALL/MARK/INTERCEPT/FOLLOW_PLAYER）的周期里，摘要标注 MY 41 / free 26 / 对手 0——模型从未收到过"对手持球"的信号，逼抢、盯防、拦截全靠"对手坐标贴着球"的位置信息间接触发。GK 甚至会在球权在客队时尝试门球分发。
BUG 5 球坐标轴语义错误：y 是高度，被当成横向 契约缺陷 · 引擎/API Layer 2 · 发现于 埋点 2 × 埋点 1 交叉验证
球 y ∈ [0.13, 0.93] 恒为高度 球 z ∈ [-3.64, 3.59] 才是横向 摘要只输出 (x, y)

发现：把 357 个周期的球坐标按字段统计：球 position.y 全部落在 0.133~0.928（均值 0.164，99% 在 ±0.5 内）——这是贴地高度；而 position.z 范围 -3.641~3.589，与球员横向坐标（±3.6）完全同量级——z 才是横向。球员是 2D (x, y 横向)，球是 3D (x, 高度 y, 横向 z)。

球的 y（高度）vs z（横向）分布
357 周期 · y 恒在 0.1~0.9（贴地高度），z 覆盖 ±3.6（横向）

影响：线上摘要的 Ball 行只输出 (x, y)，于是模型看到的球位置永远是 (x, 0.1)——横向坐标从摘要中彻底消失。日志里所有 "Ball: (-0.6, 0.1)" 的 0.1 都是高度，不是边路位置。同时 dist() 用 y 计算球距，等于把高度当横向混入所有距离计算。

模型推理层 · Reasoning Failures
两组问题发生在这里：输出结构（是否给出可执行、可解释的结构化决策）与决策行为（对最新状态是否真的响应，还是只在复读）。世界和摘要全对，模型也可能在这里出错。

BUG 6 LLM 输出缺 commandType：45% 指令是裸参数 混合 · 模型输出质量 + 解析兜底 Layer 3 · 发现于 埋点 3 · LLM 原始指令

发现：统计 LLM 原始返回的 395 条指令，179 条（45%）没有 commandType 字段——模型直接输出 {"target_x":25.0,"target_y":10.0} 这样的裸参数，靠解析层按"唯一可识别的字段"猜类型补全。

影响：解析层"尽力兜底"让整条链路表面零失败（395/395 成功下发），但这把模型的行为偏差藏进了日志——只有当埋点 3 和埋点 4 对比时才发现：模型根本没有在输出结构化决策。同时缺 playerId 也由解析层强制注入（每 agent 固定控制自己的位置号），进一步掩盖了模型对"控制谁"的无感知。

归因（LLMOps 视角）：45% 裸参数通常不是模型"能力不足"，而是 Prompt 的结构化约束不够强——未强制 JSON Schema / 未启用 Function Calling 或 Structured Outputs 等约束解码手段时，模型倾向于自由输出字段。责任在调用侧约束设计，而不在模型本身。

决策行为 指令 × 状态相关性审计：复读、无球动作、错位指令 混合 · 上游污染 + 模型自身 Layer 3 · 埋点 3 × 埋点 1 交叉验证

归因拆分（关键）：这组问题不是同一性质。无球射门（C）、无球门球分发（E）、出界移动目标（F）主要继承自上层——摘要距离失真、持球误标、场地尺度错，修掉 L1/L2 后基本消失；指令×持球错位（B）与无球传球（D）是混合，上游修对后部分消失。但复读/锁死（A）是模型自身的独立行为——43% 的状态变化无响应、69 次球权易主仍发同一条指令，即使用户把世界和摘要全部修对，只要决策层不约束"对最新状态响应"，agent 依然会"播幻灯片"。这也解释了为什么修复必须分层推进。

执行转换层 · Execution Failures
模型想做的没错，但落地走了样——1 个缺陷发生在这里：目标消歧、参数校验、坐标系夹取。

四层传导：错误如何逐级放大

单独看，每个 bug 都"不大"；但它们不是孤立存在的。把上一章各层的缺陷串起来，会看到一条清晰的传导路径——上一层的输出是下一层的输入，错误沿着这条链逐级放大：

L1 · 世界状态层
· agentId 两队复用（BUG 1）
· 文档 ±55 vs 实际 ±6.4（BUG 2）
错误源头：世界状态本身带歧义
→
L2 · 上下文层
· 球门硬编码 ±55（BUG 3）
· next() 无消歧 → 持球恒 MY（BUG 4）
· 球 y=高度当横向（BUG 5）
模型看到的世界被系统性写错
→
L3 · 模型推理层
· 在 ±55 世界里规划 → 出界（BUG 2 延续）
· 信"本队持球" → 攻防颠倒（BUG 4 延续）
· 输出裸参数、缺类型（BUG 6）
· 复读：状态变化 43% 无响应、球权易主仍同指令（决策行为，模型自身）
在错误前提下做错误决策 + 自身决策退化
→
L4 · 执行转换层
· target_player_id 无队伍维度（BUG 7）
· 解析层兜底掩盖模型问题（BUG 6）
错误被"成功"地执行下去
为什么修一个地方不够：即使修掉 L2 的持球误标，L1 的编号复用仍让 target 无法消歧；即使修掉 L1，L2 的球门硬编码仍让 LLM 在 ±55 的世界里规划；即使全部修对摘要，L4 的解析层仍会把出界坐标原样下发。要扭转 0:2 的结果，需要的是整条链的一致性修复，而不是任何单一补丁。这也正是"分层定位"与"逐层修复"必须配套的原因。

从 Bug 到 Agent Observability

这场比赛最终输了 0:2。但比分并不是本文最重要的发现。更重要的是，通过四个埋点，我们第一次能够回答：Agent 的错误究竟发生在哪一层。下面的归因清单把 7 个案例压缩成一张排查表，供任何 Agent 系统直接套用。

七个案例，压缩成一张归因清单

框架本身已在 01 章建立，这里只留案例与排查手段：

层次本文案例排查手段对应埋点切面
L1 世界状态BUG 1 · BUG 2字段全量扫描：编号唯一性、坐标尺度、轴语义埋点 1
L2 上下文BUG 3 · BUG 4 · BUG 5摘要声明 vs 原始数据交叉验证埋点 2 × 1
L3 模型推理BUG 6 · 决策行为审计字段完整度、对状态变化的响应性；指令×真实持球交叉埋点 3 / 3×1
L4 执行转换BUG 7模型输出与下发指令对比埋点 3 × 4
可观测性正在变成新的基础设施：对越来越复杂的 Multi-Agent 系统而言，Prompt 已经不再是主要调试对象——当五个 agent 共享世界、各自决策、互相影响时，调试对象是"状态在层与层之间如何失真"。分层的日志切面，就是把不可见的失真变成可见的路径。这一框架并不属于足球：换成 AI Customer Service、AI Coding Agent、AI Research Agent、AI Operations Agent，四层结构完全一样。
修复必须分层，因为问题分层：决策行为审计给出了一条硬结论——无球射门、无球门球分发、出界移动目标主要继承自上层的摘要失真（修 L1/L2 基本消失）；但复读（43% 状态变化无响应、69 次球权易主仍同指令）是 L3 模型自身的独立问题，上游全修对也不会消失。只修系统不修决策，agent 依然会"播幻灯片"——每一层的问题，要在每一层修。
